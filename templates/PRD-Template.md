> **PRD Type Definitions:**
> - **Maintenance**: Bug fixes, technical debt, minor enhancements — low complexity, contained scope
> - **Incremental Improvement**: Meaningful enhancements to existing functionality — measurable growth within existing markets
> - **Strategic Request**: Customer-driven feature work — validate broad applicability, avoid bespoke complexity
> - **Growth Initiative**: New products, new user segments, or new markets — expanding beyond current footprint

## 11. Agent Handoff Instructions

> This section is written for AI-assisted development teams or autonomous agents.
> It consolidates everything needed to begin implementation without ambiguity.
> Human teams may skip this section — all requirements are fully stated above.

### 11.1 Objective
> See Section 1.2 for the full problem definition. Do not restate it here.

In plain language, the goal of this build is: [One sentence — what are we building and what should it do?]

### 11.2 Inputs
> What does the agent/team receive as inputs to begin work?

- [ ] This PRD (requirements and acceptance criteria)
- [ ] Design assets: [Link]
- [ ] API documentation: [Link]
- [ ] Existing codebase context: [Repo / branch / folder]
- [ ] Test data / sandbox credentials: [Link or location]

### 11.3 Explicit Constraints
> Hard rules that must not be violated under any circumstances.

- **Do not** store raw payment card data — tokenization is required
- **Do not** modify the existing [X] service — integrate via API only
- **Do not** deploy to production — deliver to staging environment only
- **Do not** introduce new external dependencies without approval
- [Add constraints specific to your environment]

### 11.4 Ambiguity Protocol
> What to do when something is not covered by this PRD.

1. Check the Open Questions log (Section 9) first
2. Default to the most conservative interpretation that satisfies the requirement
3. Flag the ambiguity as a comment in the PR — do not silently choose
4. Do not block on minor unknowns — implement with a clearly marked `TODO`
5. Log any new questions discovered during development in Section 9

### 11.5 Definition of Done
> Work is complete when ALL of the following are true.

- [ ] All P0 requirements in Section 4 are implemented
- [ ] All P0 acceptance criteria in Section 5 are passing
- [ ] All test cases in Section 10.1 pass
- [ ] No regressions in [existing feature / test suite]
- [ ] Code is documented and follows [style guide / conventions link]
- [ ] Test results are filled into Section 10
- [ ] Any deviations from requirements are documented with rationale
- [ ] PR submitted to [branch] with staging deployment link confirmed
